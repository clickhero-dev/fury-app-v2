Autenticação e Autorização

JWT · Redis · bcrypt · SHA‑256
AUTH‑01Auth · DesignAtivo
Tokens rotativos com hash SHA‑256 armazenado no Redis
access token expira em 15 minutos. refresh token expira em 7 dias. Cada refresh token é hasheado (SHA‑256) e persistido no Redis com TTL de 7 dias. Na rota POST /auth/refresh, o hash é comparado com crypto.timingSafeEqual para evitar timing attacks. No logout, a hash é removida do Redis imediatamente.
Segredos: JWT_SECRET e JWT_REFRESH_SECRET separados, ambos obrigatórios (crash startup se ausentes).
AUTH‑02Auth · MiddlewareAtivo
Middleware de autenticação duplo (JWT + mock quickstart)
authMiddleware: extrai Bearer token, verifica com verifyAccessToken. Em desenvolvimento (AUTH_BYPASS_DEV=true + NODE_ENV≠production), aceita tokens mock (base64 JSON com userId). authSSEMiddleware: variante para EventSource — aceita token por query string ou header.
AUTH‑03Auth · TenantAtivo
Tenant middleware — isolamento multi‑tenant
tenantMiddleware: garante que todo request autenticado tenha tenantId no JWT. Se ausente, retorna 403 (não 401 — o usuário está autenticado, mas sem contexto de tenant). Isso impede vazamento de dados entre tenants.
AUTH‑04Auth · RotasAtivo
Rotas públicas vs protegidas
Públicas (10): /auth, /health, /meta, /studio, /fury, /goals, /billing, /budget, /automation, /openrouter.
Protegidas (7): /campaigns, /dashboard, /metrics, /instagram, /forms, /brand‑kit, /observability.
/admin usa proteção por role (superadmin) — rota separada.

Segurança e Rate Limiting

Redis · Sliding Window · Lua · CORS · Helmet
SEC‑01Rate Limit · RedisAtivo
Sliding window atômico no Redis (Lua script)
Limite padrão: 100 requisições por segundo por IP. A janela é de 1 segundo (configurável via RATE_LIMIT_WINDOW_MS). O Redis executa um script Lua atômico: ZREMRANGEBYSCORE → conta entradas na janela → se ≥ limite, rejeita; senão adiciona entrada com timestamp. Resposta 429 inclui headers: X‑RateLimit‑Limit, X‑RateLimit‑Remaining, Retry‑After.
IP real: usa x‑forwarded‑for (proxy reverso) → req.ip → socket.remoteAddress.
Desabilitável: RATE_LIMIT_ENABLED=false ou NODE_ENV=test. Health checks (/health) nunca consomem cota.
SEC‑02CORS · ExpressAtivo
CORS dinâmico com credentials
CORS configurado com callback que aceita qualquer origin (callback(null, true)) + credentials: true. Adequado para SaaS multi‑tenant onde domínios customizados são frequentes.
Atenção: allow‑origin: * com credentials expõe cookies de sessão. Como a API usa Authorization header (Bearer), o risco é mitigado. Em produção com cookies, restringir origem.
SEC‑03Error Handler · SegurançaAtivo
Sem vazamento de stack traces
O errorHandler retorna sempre { success: false, error: { code, message } }. Para erros inesperados, retorna INTERNAL_SERVER_ERROR com mensagem genérica ("An unexpected error occurred"). Stack traces não são expostos. Erros de validação Zod retornam array de erros por campo, mas sem dados sensíveis.
SEC‑04Auth · RefreshAtivo
Refresh token armazenado como hash (não plaintext)
O refresh token nunca é armazenado em texto plano. É hasheado com SHA‑256 e o hash é salvo no Redis com chave refresh:{userId}. A comparação usa timingSafeEqual — resistente a timing attacks. No logout, a hash é removida (DEL). Se um atacante obtiver o hash, não pode derivar o token original.
SEC‑05Auth · SenhasAtivo
bcrypt com salt rounds
Senhas armazenadas com bcrypt.hash(password, 12). Comparação com bcrypt.compare. Email verificado via OTP de 6 dígitos antes de liberar acesso completo. Reset de senha via token único enviado por email.

Filas, Workers e Infraestrutura

BullMQ · Redis · Docker · Traefik
INFRA‑01Queue · DesignAtivo
4 filas BullMQ independentes com singleton Redis
Cada fila usa uma conexão Redis dedicada (duplicate()) obtida via singleton lazy‑loading. A conexão é reutilizada — se já estiver criando, aguarda a mesma Promise.

Filas ativas:
• compliance‑check — validação de conformidade de anúncios
• studio‑generation — geração de criativos (GPU‑bound, assíncrono)
• budget‑optimizer — otimização de orçamento
• sync‑jobs — sincronização periódica Meta ↔ banco local

Engines (schedulers):
• rule‑engine — dispara regras de automação
• fury‑engine — engine principal FURY
INFRA‑02Server · ConfigAtivo
Timeouts HTTP ajustados para requisições longas
server.timeout = 60s, keepAliveTimeout = 65s, headersTimeout = 66s. Evita que o Traefik retorne 502 Bad Gateway antes do Node.js concluir geração de imagem (que pode levar 20‑40s).
INFRA‑03Docker · DeployAtivo
Container com healthcheck, restart e network isolada
docker‑compose.api.yml expõe porta 3001→3000, com healthcheck HTTP a cada 30s. network_mode: infra_fury‑network (rede externa compartilhada com Redis e PostgreSQL). extra_hosts mapeia IPs fixos para fury‑postgres e fury‑redis. restart: unless‑stopped.
INFRA‑04Seed · StartupAtivo
Seed automático na inicialização
seedStartup() roda antes do servidor aceitar requests — garante que superadmin + tenants demo existam. Ambiente test pula seed e workers.

Recomendações e Próximos Passos

Priorizado por impacto × esforço
Alta prioridade — baixo esforço
REC‑01Roteamento · AcessoRecomendado
Aplicar auth nas rotas públicas de billing e budget
/billing e /budget operam dados financeiros sem middleware de auth. Basta adicioná-los ao array AUTH_TENANT_SUB em routes/index.ts — uma linha por rota.
Impacto: evita exposição de dados de faturamento e orçamento a requests não autenticados. Esforço: ~2 linhas.
REC‑02CORS · SegurançaRecomendado
Restringir CORS a origens conhecidas em produção
Hoje callback(null, true) aceita qualquer origin. Em produção, validar contra lista de domínios permitidos (tenant custom domains + domínio principal). Fallback para null só em dev.
Impacto: reduz superfície de CSRF. Esforço: ~15 linhas com array de origins + env var.
REC‑03Testes · QualidadeRecomendado
Dobrar cobertura de testes — mirar 40%
Atualmente ~20% (5.379 linhas de teste para 25.932 de código). Priorizar testes unitários nos services: auth.service, campaigns.service, meta.service, studio‑image.service. Cada service com 2-3 cenários de sucesso + 1 de erro.
Impacto: reduz regressões em deploys. Esforço: ~30-40 testes novos, 2-3 dias de trabalho.
Média prioridade — médio esforço
REC‑04Rate Limit · RefinamentoRecomendado
Rate limiting por rota, não global
O sliding window atual é global (100 req/s por IP em todas as rotas). Separar limites: /auth/register (5/min), /auth/login (10/min), /studio (20/min, é GPU‑bound), rotas CRUD (100/s mantido). A estrutura de middleware já suporta — adicionar chave por rota no Redis.
Impacto: protege endpoints sensíveis sem estrangular uso normal. Esforço: refatorar rateLimitMiddleware para aceitar config por path — ~40 linhas.
REC‑05Observabilidade · LogsRecomendado
Adicionar request ID e tracing básico
O logger atual (console.log) não inclui requestId nem tenantId. Adicionar middleware que gera UUID por request e injeta no req + header X‑Request‑Id. Permite rastrear erros ponta a ponta.
Impacto: debug de produção muito mais rápido. Esforço: ~20 linhas de middleware + adoção no error handler.
REC‑06Auth · HardeningRecomendado
Remover mock token de produção
AUTH_BYPASS_DEV é seguro (só funciona com NODE_ENV≠production), mas o código de mock token fica no bundle de produção. Extrair para módulo separado que só é importado em dev — evita superfície de ataque.
Impacto: hardening — nenhuma vulnerabilidade ativa, mas reduz superfície. Esforço: extrair função mock para arquivo condicional.
REC‑07Studio · PerformanceRecomendado
Timeout progressivo nas chamadas OpenRouter
studio.routes.ts (809 linhas) é o arquivo mais extenso. Geração de imagem pode levar 20-40s. Adicionar timeout configurável por provider + feedback parcial (SSE) enquanto imagem é gerada — evita que o cliente veja "loading infinito".
Impacto: UX do estúdio mais responsiva. Esforço: SSE já existe (authSSEMiddleware) — adaptar.
Baixa prioridade — quando houver tempo
REC‑08Docker · InfraOpcional
Migrar extra_hosts para DNS interno
IPs fixos (172.26.0.3, 172.26.0.2) quebram se containers reiniciarem em ordem diferente. Usar nomes de serviço DNS do Docker Compose (rede compartilhada resolve por container name).
Impacto: elimina falha de deploy por IP fixo. Esforço: baixo — só remover extra_hosts e confiar no DNS interno.
REC‑09Rate Limit · EscalaFuturo
Substituir sliding window por token bucket se escala exigir
Sliding window com ZSET escala bem até ~10K req/s por Redis. Acima disso ou com custo de Redis elevado, migrar para token bucket (1 chave string + INCR + EXPIRE). Não necessário agora.
Gatilho: latência de Redis >5ms no rate limit ou custo de infra subindo. Esforço: ~30 linhas, swap do script Lua.
REC‑10Queue · ResiliênciaFuturo
Dead letter queue para jobs que falham ≥3x
Jobs que falham repetidamente são descartados pelo BullMQ. Adicionar DLQ para inspeção manual — evita perda silenciosa de jobs.
Impacto: visibilidade de falhas. Esforço: configurar removeOnComplete e handler de falha — ~20 linhas.
